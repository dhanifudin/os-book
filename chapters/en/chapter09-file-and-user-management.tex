\chapter{File, User, and Group Management}
\label{ch:file-and-user-management}

\chapterhero{green}{Control access permissions, ownership, user accounts, groups, and sudo to keep your system secure and easy to manage.}{\faLock\quad permissions}{\faUserShield\quad ACL}{\faUserCog\quad sudo}

When you create a new account in Ubuntu, the system immediately gives that account full ownership of its home directory. Other accounts cannot read its contents unless given explicit permission. This is not an additional feature, but rather the basic design of Linux as a multi-user system: each file and directory has three identities, namely the owner user (\textit{owner}), the associated group, and all other users, and access is managed separately for each group.

This chapter combines file permission management and user identity administration. The discussion starts from the standard permission model \texttt{rwx} along with the commands \cmd{chmod}, \cmd{chown}, and \cmd{chgrp}, then continues to special permissions such as \textit{setuid}, \textit{setgid}, and \textit{sticky bit}, then Access Control List (ACL), user and group account management, delegation of administrative rights via \cmd{sudo}, and limiting disk space with quotas.

In multi-user systems such as campus servers or production machines, proper access control is the foundation of security. Incorrect configuration can make sensitive data unreadable to everyone, or give someone more power than they should.

By the end of this chapter, you will be able to:

\item create, modify, and delete user accounts and groups with appropriate commands;
\item manage group membership and understand file structures \file{/etc/passwd}, \file{/etc/shadow}, and \file{/etc/group};
\item configure limited \cmd{sudo} rights via \file{/etc/sudoers.d/} securely; and

\end{enumerate}

\section{Access Permissions and File Ownership}
\label{sec:advanced-permissions}
%% ========================================================================

Every file in Linux has three permission groups: \textit{owner}, \textit{group}, and \textit{others}. Each group has a combination of read (\texttt{r}), write (\texttt{w}), and execute (\texttt{x}) permissions. The \cmd{chmod} command changes these permissions, while \cmd{chown} and \cmd{chgrp} change user and group ownership. On top of the nine standard permission bits, Linux also has three additional bits called \textit{special permission bits}: setuid, setgid, and sticky bit.

\textbf{Setuid (SUID)} makes a program run with the identity of the file owner, not the identity of the user running it. The most obvious example is \cmd{/usr/bin/passwd}: this command needs to write to \file{/etc/shadow} which can only be written by \texttt{root}, but normal users should be able to change the password themselves. The solution is to setuid on \cmd{passwd}, so that whoever runs the command, the process runs as \texttt{root}.

\textbf{Setgid (SGID)} works similarly to setuid, but for groups. In executable files, processes run with the file's GID. On a directory, setgid has a different effect: any new files created in that directory automatically inherit the directory group, not the file's primary group. This is especially useful for team collaboration directories.

The \textbf{Sticky bit} in a directory means that only the file owner can delete the file themselves, even if the directory is writable by multiple users. The \dir{/tmp} directory uses the sticky bit because all users need to create temporary files there, but cannot delete files belonging to other users.

In octal notation, these three special bits occupy the fourth digit in front:

\begin{itemize}
\item \texttt{4xxx} for setuid
\item \texttt{2xxx} for setgid
\item \texttt{1xxx} for sticky bits
\item These three items can be combined. For example, \texttt{6xxx} means setuid and setgid are active at the same time.
\end{itemize}

\begin{lstlisting}[language=bash, caption={Observe and set special bits}]
# observe the SUID in passwd
ls -l /usr/bin/passwd
# output: -rwsr-xr-x 1 root root ... /usr/bin/passwd
# The letter 's' replaces 'x' in the owner's execute position

# observe the sticky bit on /tmp
ls -ld /tmp
# output: drwxrwxrwt 15 root root ... /tmp
# The letter 't' replaces 'x' in the execute others position

# create a directory with SGID
sudo mkdir /srv/projek-bersama
sudo chown root:developers /srv/projek-bersama
sudo chmod 2775 /srv/projek-bersama
ls -ld /srv/projek-bersama
# output: drwxrwsr-x ... group developers

# add sticky bit to shared directory
sudo chmod 3775 /srv/projek-bersama
ls -ld /srv/projek-bersama
# output: drwxrwsr-t ... (SGID + sticky bit on)
\end{lstlisting}

Apart from bit permissions, Linux also recognizes \textit{extended file attributes} which are managed with \cmd{chattr} and read with \cmd{lsattr}. The most common attribute is \texttt{i} (\textit{immutable}): files with this attribute cannot be modified, deleted, or renamed even by \texttt{root}, unless the attribute is revoked first.

\begin{lstlisting}[language=bash, caption={Extended attributes with chattr and lsattr}]
# create important configuration files
sudo touch /etc/app-config-kritis.conf

# install immutable attribute
sudo chattr +i /etc/app-config-kritis.conf

# try deleting (will fail)
sudo rm /etc/app-config-kritis.conf
# rm: cannot remove ...: Operation not permitted

# see attributes
lsattr /etc/app-config-kritis.conf
# output: ----i------------ /etc/app-config-kritis.conf

# revoke immutable attribute
sudo chattr -i /etc/app-config-kritis.conf
\end{lstlisting}

\section{Access Control Lists (ACLs)}
\label{sec:acls}
%% ========================================================================

Standard Unix permissions recognize only three entities: owner, group, and all other users. Imagine this situation: financial report files are owned by the \texttt{alice} and \texttt{finance} groups. An IT director named \texttt{bob} needs to read that file for the audit, but you don't want to add \texttt{bob} to the \texttt{finance} group because that would give him access to all of that group's files. With standard permissions, there is no clean solution. This is where ACLs come in.

\textit{Access Control List} (ACL) is an additional layer on top of standard Unix permissions. ACLs let you define permissions for specific users or groups individually, without changing the file owner or group membership. There are two types of ACLs: \textit{access ACL} which applies to a specific file or directory, and \textit{default ACL} which is inherited by new files in a directory.

On Ubuntu, the \texttt{acl} package is usually available. The two main commands are \cmd{getfacl} to read ACLs and \cmd{setfacl} to modify them.

\begin{lstlisting}[language=bash, caption={Basic ACL installation and checking}]
# make sure the acl package is available
sudo apt install -y acl

# create a test file
echo "Q4 financial report" > report.txt
chmod 640 report.txt

# read standard ACL (no additional entries yet)
getfacl report.txt
# output:
# file: report.txt
# owner: alice
# group: finance
# user::rw-
# group::r--
# other:::
\end{lstlisting}

When a file has no additional ACLs, \cmd{getfacl} displays only three entries equivalent to standard Unix permissions. The ACL entry format follows the \texttt{tipe:nama:izin} pattern. For example, \texttt{u:bob:r--} means user \texttt{bob} gets read permission, and \texttt{g:audit:rw-} means group \texttt{audit} gets read and write permission.

\begin{lstlisting}[language=bash, caption={Adding and removing ACL entries}]
# give user bob read rights
setfacl -m u:bob:r report.txt

# grant the audit group read and write rights
setfacl -m g:audit:rw report.txt

# look at the results : note the new entries and the mask
getfacl report.txt

# ls -l now displays a '+' sign at the end of permissions
ls -l report.txt

# delete ACL for bob only
setfacl -x u:bob report.txt

# remove all additional ACLs at once
setfacl -b report.txt
\end{lstlisting}

When additional ACLs are installed, Linux automatically creates a \textbf{mask} entry. The mask serves as an effective permission upper limit for all ACL entries except owner and others. If the mask is set to \texttt{r--}, then entry \texttt{g:audit:rw-} will only be effective as \texttt{r--}. The comment \texttt{\#effective:} in the output of \cmd{getfacl} shows the permissions actually apply.

\textbf{Default ACL} is very useful for shared project directories. Any new files or subdirectories created in a directory with a default ACL will automatically inherit those ACL rules.

\begin{lstlisting}[language=bash, caption={Default ACL on project directory}]
mkdir proyek-data

# set default ACLs so that new files can be accessed by the developers group
setfacl -d -m g:developers:rwx proyek-data
setfacl -d -m u:deploy:r-x proyek-data

# look at the default ACLs on the directory
getfacl proyek-data

# create a new file and check its ACL
touch proyek-data/data-baru.csv
getfacl proyek-data/data-baru.csv
# new files automatically inherit ACLs from the parent directory

# remove default ACLs on directories
setfacl -k proyek-data
\end{lstlisting}

\section{User Management}
\label{sec:user-management}
%% ========================================================================

Linux stores user information in three main files. \file{/etc/passwd} contains basic data such as username, UID, primary GID, home directory, and login shell. This file can be read by all users because many programs require this information. \file{/etc/shadow} stores password hashes and account expiration policies. This file can only be read by \texttt{root} because it contains sensitive cryptographic data. \file{/etc/group} lists all groups and their members.

The single line format in \file{/etc/passwd} looks like this:

\begin{lstlisting}[language=bash, caption={File format /etc/passwd}]
# name:x:UID:GID:comments:home-directory:shell
alice:x:1001:1001:Alice Programmer:/home/alice:/bin/bash
\end{lstlisting}

The second column is always \texttt{x}, indicating that the password hash is stored in \file{/etc/shadow}. UID under 1000 is usually used by system accounts, while UID 1000 and above is for human user accounts.

The main commands for user management are \cmd{useradd} to create a new account, \cmd{usermod} to modify, and \cmd{userdel} to delete. The \cmd{passwd} command is used to set or change a password. Use \cmd{id} and \cmd{getent passwd} to read user information.

\begin{lstlisting}[language=bash, caption={User account lifecycle}]
# create a new user with a home directory and a shell
sudo useradd -m -s /bin/bash student01
sudo passwd student01

# verify the newly created account
id student01
getent passwd student01
ls -ld /home/student01

# modify: add to additional groups
sudo usermod -aG sudo student01

# modification: change login shell
sudo usermod -s /bin/sh student01

# account lock (prevent login)
sudo usermod -L student01
sudo passwd -S student01
# output: student01 L ... (L = locked)

# unlock the account again
sudo usermod -U student01

# delete the account along with the home directory and mailbox
sudo userdel -r student01
\end{lstlisting}

Note the \texttt{-aG} option in \cmd{usermod}. The \texttt{-a} option means \textit{append}: add a new group without removing existing group membership. Without \texttt{-a}, the \texttt{-G} option will replace all additional groups at once, which often results in users losing access to previously available services.

The \cmd{who} and \cmd{w} commands are useful for seeing who is currently logged in. \cmd{who} displays a list of active sessions, while \cmd{w} provides more complete information including currently executing commands.

\begin{lstlisting}[language=bash, caption={Check active user sessions}]
who
w
last | head -20
# last displays login and logout history
\end{lstlisting}

\section{Group Management}
\label{sec:group-management}
%% ========================================================================

Groups in Linux function like divisions in an office. By making users members of the right groups, one permission rule can apply to many people at once. Instead of setting permissions individually for each user, you can create group \texttt{pengembang}, put all the developers in there, and then set project directory permissions for that group.

Each user has one \textit{primary group} logged in \file{/etc/passwd} and \file{/etc/group}. Users can also be members of many \textit{additional groups}. Additional group membership information is stored in \file{/etc/group}.

One line format in \file{/etc/group}:

\begin{lstlisting}[language=bash, caption={File format /etc/group}]
# group-name:x:GID:member1,member2,...
developers:x:1050:alice,bob,charlie
\end{lstlisting}

The main group management commands are \cmd{groupadd} to create a new group, \cmd{groupmod} to change group properties, \cmd{groupdel} to delete, and \cmd{gpasswd} to manage membership.

\begin{lstlisting}[language=bash, caption={Basic operations of group management}]
# create a new group
sudo groupadd pengembang
sudo groupadd -g 2050 desainer
# the -g option specifies the GID explicitly

# change group name
sudo groupmod -n devteam pengembang

# add user to group with gpasswd
sudo gpasswd -a alice devteam
sudo gpasswd -a bob devteam

# remove user from group
sudo gpasswd -d bob devteam

# view group members
getent group devteam

# delete group (only if it is not anyone's primary group)
sudo groupdel desainer
\end{lstlisting}

Once added to a new group, users need to log out and log back in for group changes to take effect in the new session. An alternative without logging out is to use \cmd{newgrp} to open a subshell with a different active group.

\begin{lstlisting}[language=bash, caption={Activate a new group without logging out}]
# view currently active groups
id
groups

# activate a new group in the current session
newgrp devteam
# verify changes
id
# type 'exit' to return to the previous shell
\end{lstlisting}

\section{Sudo configuration}
\label{sec:sudo-config}
%% ========================================================================

In the real world, system administrators rarely work directly as \texttt{root}. Instead, they use a regular account and run certain commands with elevated privileges using \cmd{sudo}. Think of \cmd{sudo} like a receptionist in an office who can ask the manager for permission on your behalf to enter a certain room, without having to permanently give you the key to that room.

\cmd{su} (substitute user) is different from \cmd{sudo}. The \cmd{su -} command opens a completely new shell as another user, asking for the target user's password. Meanwhile \cmd{sudo} runs one command with elevated privileges, asks for the user's own password, and logs the activity to the system log.

\begin{lstlisting}[language=bash, caption={Differences in using su and sudo}]
# su: switches to full root shell
su -
# type the root password, then 'exit' to return

# su: run one command as another user
su - alice -c "ls /home/alice"

# sudo: run one command as root
sudo apt update

# sudo: run commands as a specific user
sudo -u www-data ls /var/www

# sudo: open root shell with login environment
sudo -i

# see what sudo privileges you have
sudo -l
\end{lstlisting}

The rule \cmd{sudo} is stored in \file{/etc/sudoers} and the files in the \dir{/etc/sudoers.d/} directory. Always use the \cmd{visudo} command to edit it because \cmd{visudo} validates the syntax before saving. Syntax errors in the sudoers file can lock administrative access to the system.

Best practice is to store additional rules in \dir{/etc/sudoers.d/} rather than editing \file{/etc/sudoers} directly. This makes management and auditing easier.

The sudoers rule format follows the pattern: \texttt{SIAPA DI-MANA=(SEBAGAI-SIAPA) PERINTAH}

\begin{lstlisting}[language=bash, caption={Example of a representative sudoers rule}]
# full access without restrictions
alice ALL=(ALL:ALL) ALL

# run apt without password
bob ALL=(root) NOPASSWD: /usr/bin/apt update, /usr/bin/apt upgrade

# Ubuntu's built-in sudo group/Debian
%sudo ALL=(ALL:ALL) ALL

# group with limited access to nginx only
%webadmin ALL=(root) /bin/systemctl start nginx, \
                     /bin/systemctl stop nginx, \
                     /bin/systemctl restart nginx

# users should only view the status of any service
charlie ALL=(root) /bin/systemctl status *
\end{lstlisting}

All usage of \cmd{sudo} is logged to \file{/var/log/auth.log} (on Ubuntu). This is important for security audits.

\begin{lstlisting}[language=bash, caption={Reading sudo logs}]
sudo grep "sudo" /var/log/auth.log | tail -20
# each log line contains: time, host, user, command executed
\end{lstlisting}

\subsection*{Lab 9.5: Configure Limited sudo Rights}

\section{Summary}
\label{sec:file-user-summary}
%% ========================================================================

In this chapter, you learned:

\begin{itemize}[noitemsep,topsep=2pt]
\item \textbf{Advanced access permissions}: setuid (4xxx) makes the program run as the owner of the file; setgid(2xxx) in the directory passes the group to the new file; sticky bit (1xxx) protects user files from deletion by others in the shared directory.
\item \textbf{Extended attributes}: \cmd{chattr +i} makes the file unmodifiable even by root; \cmd{lsattr} displays the installed attributes.
\item \textbf{ACL}: \cmd{getfacl} reads ACL, \cmd{setfacl -m} adds entry, \cmd{setfacl -x} removes one entry, \cmd{setfacl -b} removes all additional ACLs; The default ACL with the \texttt{-d} option is inherited to new files in the directory.
\item \textbf{User management}: \cmd{useradd -m -s} creates account with home directory; \cmd{usermod -aG} adds a group without deleting the old group; \cmd{userdel -r} deletes the account along with the home directory; information is stored in \file{/etc/passwd} and \file{/etc/shadow}.
\item \textbf{Group management}: \cmd{groupadd}, \cmd{gpasswd -a/-d} to add and remove members; \cmd{newgrp} activates the new group without logging out; \file{/etc/group} stores the definitions of all groups.
\item \textbf{Sudo configuration}: rules are stored in \dir{/etc/sudoers.d/} and always edited with \cmd{visudo}; \texttt{NOPASSWD} allows passwordless commands; all activities are recorded in \file{/var/log/auth.log}.
\end{itemize}

\section{Exercises}
\label{sec:user-group-exercises}
%% ========================================================================

\textbf{General Instructions}: Do all the exercises independently. Note important steps, save screenshots when necessary, then summarize the results as personal documentation.

\subsubsection*{Exercise 9.1 Permissions Audit and Collaboration Directory}
You are tasked with auditing and configuring permissions for a shared project.
\begin{enumerate}
\item Find all SUID files on the system with the command \cmd{find / -perm -4000 -type f 2>/dev/null}. Note down at least three files you find and explain why each requires SUID.
\item Create directory \dir{~/proyek-audit} with the following configuration: SGID active so that all new files inherit the directory group, sticky bit active so that users cannot delete files belonging to others. Verify with \cmd{ls -ld}.
\item Create at least three files in the directory and verify that the file groups match the directory groups.
\end{enumerate}


\subsubsection*{Exercise 9.2 Configure ACLs for the Development Team}
Simulate real team access management scenarios.
\begin{enumerate}
\item Create three user accounts: \texttt{pemimpin}, \texttt{anggota-a}, and \texttt{pengamat}. Create group \texttt{tim-dev}.
\item Create directory \dir{~/proyek-tim} and set default ACLs so that: \texttt{pemimpin} gets full access (rwx), \texttt{tim-dev} gets read and write access, \texttt{pengamat} gets read only access.
\item Create three new files in that directory and verify that each inherits the correct ACL.
\item Remove access \texttt{pengamat} from one of the files using \cmd{setfacl -x} and verify the results.
\end{enumerate}


\subsubsection*{Exercise 9.3 Account Policies and Restricted sudo}
Enforce secure account policies and delegate limited administrative rights.
\begin{enumerate}
\item Create account \texttt{staf-it} with shell \texttt{/bin/bash} and add it to group \texttt{helpdesk} (create the group first).
\item Create a file \file{/etc/sudoers.d/staf-it} using \cmd{visudo -f} that allows \texttt{staf-it} to run: \cmd{systemctl status *} (without password), \cmd{apt update} (without password), and \cmd{systemctl restart ssh} (with password).
\item Verify the configuration with \cmd{sudo -l -U staf-it} and ensure that only those three commands are listed.
\item Document the differences in rule lines for those that use \texttt{NOPASSWD} and those that don't.
\end{enumerate}
